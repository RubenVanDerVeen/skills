## Findings

### Finding 1 - fix-skill: skill-harvest digest filter leaks compaction summaries and task-notification blocks

The digest filter in `references/extraction.md` only drops lines matching `^(Base directory for this skill|<system-reminder>|<command-name>|<local-command>)`. It does not drop Claude Code context-compaction summaries or subagent `<task-notification>` / `<result>` / `<usage>` blocks, which are injected as user-role messages and so survive the filter. In this run they dominated the digest and drowned real user signals.

**Evidence (counts in the produced Claude Code digest):**
- 27 lines matching compaction-summary markers (`This session is being continued from a previous conversation`, `Summary:`, `Continue the conversation from where it left off`).
- 28 lines matching `<task-notification>`, `<result>Status:`, `<usage><subagent_tokens>`.
- Session `549da4a8-...jsonl` (project `hobby-hermes-console`): the digest for this one session is hundreds of lines of compaction summary (token-usage tables, custom-agent tables, multi-section summaries) before any real user message.
- Session `ce1dae0e-...jsonl` (project `hobby-hermes-console`): same pattern, compaction summary plus a stream of `<task-notification>` subagent-result blocks.

**Target skill:** `skill-harvest/references/extraction.md` (and the digest description in `skill-harvest/SKILL.md` step 3).

**Proposed edit sketch:**
- Extend the line-drop regex to also drop lines starting with: `This session is being continued`, `Summary:`, `Continue the conversation from where it left off`, `If you need specific details`, `<task-notification>`, `</task-notification>`, `<result>`, `</result>`, `<usage>`, `<note>`, `<status>`, `<summary>`, `<task-id>`, `<tool-use-id>`, `<output-file>`.
- Add a block-strip pass: drop everything between `<task-notification>` and `</task-notification>` inclusive (these are multi-line and the current line filter leaves their inner content behind).
- Optionally skip a file's leading compaction block entirely when its first surviving line is `This session is being continued from a previous conversation`.

## Concerns (operator attention)

These are about the skill itself, surfaced by executing it, and are outside the scope of session-mined findings:

1. **Cap-rule cursor semantics do not drain an older backlog under newest-first processing.** The skill enumerates newest-first and caps at 40, but the state query uses strict `>` against the cursor. With newest-first ordering, no cursor value both avoids re-processing the top 40 and reaches older backlog sessions: a `>` query only reaches newer sessions. Per the documented rule this run set each cursor to the oldest unprocessed session's time (oldest in window), which keeps the backlog reachable (nothing orphaned) but means the next run re-enumerates the full set and re-digests the same newest 40. Backlog sessions below the top 40 will not actually drain until the corpus stops growing or a project filter narrows the window. Suggested design follow-up: either process oldest-first when a backlog exists, or use a two-sided time window / last-processed-session-id watermark instead of a single timestamp.

2. **Strict `>` orphans the single oldest session.** Setting the cursor to the oldest session's own mtime and querying `>` excludes that exact session next run. Minor (one session), but worth a note. Using `>=` or subtracting one second would be more correct.

3. **Observer-noise overlap.** Finding 5 (exclude `claude-mem-observer`) addresses the largest noise source in the Claude Code backlog directly.
